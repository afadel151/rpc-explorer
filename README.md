# RPC Explorer & Benchmark Lab

**Owner:** Fadel Akram, Group SIAD

An interactive, research-based demonstrator for exploring Remote Procedure Call (RPC) middleware concepts, comparing a custom JSON-over-TCP implementation against modern gRPC (Protobuf), and contrasting both with REST (FastAPI).

This project was built to illustrate distributed systems concepts including localization transparency, stubs/skeletons, marshalling/unmarshalling, network failure simulation, and interface definition contracts.

## Project Scope

This laboratory focuses explicitly on the mechanics of RPC and network resilience. It supports:
- **Custom JSON/Socket RPC:** A from-scratch implementation to expose what middleware actually does.
- **gRPC (Unary + Streaming):** Modern RPC using Protocol Buffers.
- **REST (FastAPI):** A standard HTTP/JSON baseline.
- **Fault Proxy:** A custom TCP proxy allowing for latency injection, connection drops, and simulated timeouts.
- **Micro-benchmarks:** Time and serialized payload size comparisons for the three transports.
- **Failure & Idempotency Demos:** Showcasing how network timeouts require retry policies and idempotency keys to avoid double-charging (e.g., in stock decrements).

### Out of Scope
The following are intentionally **out of scope** to keep the codebase focused on core RPC transport mechanics:
- TLS / Encryption
- Authentication & Authorization
- Real databases (inventory is an in-memory thread-safe dictionary)
- Web UI (the lab uses an interactive Typer+Rich CLI)
- Custom-RPC streaming frames (batch-only for custom RPC)
- Service discovery and Load balancing

## Benchmarks & Performance: Context Matters

The benchmarks generated by this lab measure **Python and implementation framework overhead** along with serialization/transport efficiency. 

> **Important Disclaimer regarding REST:** The REST implementation utilizes FastAPI, Uvicorn, and Pydantic. Any benchmark numbers labeled as REST inherently include significant ASGI and framework overhead. **These benchmarks must not be used to conclude that "HTTP is slow".** 

### Comparative Analysis Points

The laboratory compares the transports across multiple dimensions. **We do not claim that RPC is universally better than REST.** Instead, we highlight the trade-offs:

1. **Invocation Model:** Calling `service.update_stock()` directly (RPC) vs. constructing `POST /products/{id}/stock` with a JSON payload (REST).
2. **Interface Definition:** Implicit and dynamic (Custom RPC), explicit IDL via `.proto` (gRPC), vs OpenAPI schemas (REST/FastAPI).
3. **Serialization:** Text-based UTF-8 JSON vs. binary Protobuf encoding. Time-to-serialize vs debuggability.
4. **Developer Experience:** Generated stubs with autocomplete vs manual HTTP clients.
5. **Contract Enforcement:** Strict type mapping at the network boundary.
6. **Evolvability and Breaking Changes:** How each protocol handles added, removed, or renamed fields across different application versions.

## Setup and Development

This project uses Python 3.12 managed by `uv`.

```bash
# Sync dependencies
uv sync

# Generate protobuf stubs
uv run python scripts/dev.py proto

# Run tests
uv run python scripts/dev.py test

# Verify environment
uv run python -m rpclab doctor
```
